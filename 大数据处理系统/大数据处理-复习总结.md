## 一、核心知识点梳理

### 第一章 大数据存储与处理基础

#### 1.1 大数据特征（5V特征）

|特征|含义|挑战|
|-|-|-|
|**Volume（大容量）**|数据量巨大（TB/PB/ZB级）|存储成本高、处理速度慢、需要分布式存储|
|**Velocity（快速性）**|数据产生和处理速度快，实时性要求高|需要流处理技术、低延迟响应|
|**Variety（多样性）**|结构化、半结构化、非结构化数据并存|数据格式多样、难以统一处理|
|**Value（价值低）**|价值密度低，海量数据中有用信息少|需要"沙里淘金"、数据提纯困难|
|**Veracity（准确性）**|数据准确性、可信赖度难以保证|数据质量参差不齐、存在噪声和误导信息|

**关键数据：**

* 2010年全球正式进入ZB时代
* IDC预计到2020年，全球将拥有40ZB的数据量
* 2017年"双11"天猫支付峰值达每秒3.3万笔交易，数据库峰值达每秒4200万次
* 2017年微信日平均用户9.02亿，每月发送消息111400亿条

#### 1.3 大数据文件系统

**1. HDFS（Hadoop Distributed File System）**

* 基于Java的分布式文件系统
* 支持PB级数据，上千个低成本商用硬件节点
* 主/从架构：NameNode（主）+ DataNode（从）

**2. GFS（Google File System）**

* 三类角色：Client（客户端）、Master（主服务器）、Chunk Server（数据块服务器）

**HDFS数据写入流程：**

1. 业务应用调用HDFS Client API请求写入文件
2. HDFS Client联系NameNode，NameNode在元数据中创建文件节点
3. 业务应用调用write API写入文件
4. HDFS Client从NameNode获取数据块编号、位置信息，联系DataNode建立流水线
客户端写入数据到DataNode1，DataNode1复制到DataNode2、DataNode3
5. 写完的数据返回确认信息给HDFS Client
6. 所有数据确认完成后，业务调用close关闭文件
7. HDFS Client联系NameNode确认数据写完成，NameNode持久化元数据

**HDFS数据读取流程：**

1. 业务应用调用HDFS Client API打开文件
2. HDFS Client联系NameNode获取文件信息（数据块、DataNode位置）
3. 业务应用调用read API读取文件
4. HDFS Client根据信息联系DataNode获取数据块（采用就近原则）
5. HDFS Client与多个DataNode通讯获取数据块
6. 数据读取完成后，业务调用close关闭连接

**HDFS副本放置策略：**

**副本距离计算公式：**

* Distance(Rack1/D1, Rack1/D1) = 0（同一台服务器）
* Distance(Rack1/D1, Rack1/D3) = 2（同一机架不同服务器）
* Distance(Rack1/D1, Rack2/D1) = 4（不同机架）

**副本放置规则：**

1. 第一个副本：在本节点（如果写请求方是DataNode）或随机选择
2. 第二个副本：在远端机架的节点
3. 第三个副本：如果前两个在同一机架，则选其他机架；否则选第一个副本同机架的不同节点
4. 第四个及以上：随机选择

**HDFS一致性模型：**

* "一次写入，多次读取"模型
* 仅当所有数据块都写成功时才返回客户端成功确认
* 保证任意DataNode都能读到最新完整数据

#### 1.4 大数据处理模式

**1. 并行处理（Flynn分类法）**

|类型|名称|特点|
|-|-|-|
|SISD|单指令单数据流|传统串行计算机|
|SIMD|单指令多数据流|向量处理器|
|MISD|多指令单数据流|极少见|
|MIMD|多指令多数据流|多核处理器、分布式系统|

**2. 分布式处理模型**

**BSP模型（大同步并行）：**

* 计算由一系列超级步组成
* 每个超级步包含三个阶段：本地计算 → 全局通信 → 路障同步
* 属于分布式存储的MIMD
* 计算和通信分开，硬件实现全局同步

**LogP模型：**

* 面向分布式存储器、点对点通信的多计算机系统并行计算模型

**3. 控制流 vs 数据流**

|特性|控制流|数据流|
|-|-|-|
|模型|控制流图（CFG）|数据流图（DFG）|
|执行方式|显式编写控制流|数据到达触发计算|
|特点|线性存储、单条执行|有向图、输入触发节点|
|效率|受存储器读写和同步影响|速度快2-3个数量级|

#### 1.7 大数据面临的挑战

**1. 可扩展性**

* Jim Gray将可扩展问题列为信息技术领域16个长远问题之首
* 挑战：如何设计高可扩展、低成本、快速响应的大数据存储和处理系统

**2. 数据多样化**

* 文本、图像、图形、视频、位置信息、手机呼叫、邮件、链接信息等
* 在线流数据、离线批处理等
* 大数据中垃圾和珍宝并存，需要"大海捞针"、去伪存真

**3. 传统算法失效**

* 多项式时间算法O(N^k)，N太大
* 需要计算复杂性和算法设计理论变革
* 从确定性计算到非精确性计算（如推荐系统只需前10名，允许一定误差）
* 简单方法+大数据集可能取得很好结果（Google Brants研究）

**4. 设计思维转变**

* **数据为中心的计算架构**：挖掘数据并行度、减少数据访问开销
* **化繁为简**：放松一致性约束，追求高可扩展、高吞吐率、高可靠性
* **弱化数据一致性**：

  * 关系数据库：强一致性（ACID）
  * 分布式环境：牺牲一致性换取可用性
  * 大数据应用具有弹性，可接受近似结果
  * 保证弱（最终）一致性即可

### 第二章 分布式存储系统

#### 2.1 分布式存储系统介绍

**定义：** 将为数众多的普通计算机或服务器通过网络连接，对外提供整体存储服务

**特性：**

* 高性能
* 可扩展
* 低成本
* 易用性

**关键技术问题：**

1. **数据分布**：解决如何将数据存储在不同节点上，实现负载均衡
2. **复制与一致性**：多副本系统中保持副本间一致性
3. **容错机制**：故障检测（心跳）、租约机制
4. **可扩展性**：突破集中存储瓶颈，弹性收缩

**容错指标：** 可用性、可靠性、安全性、可维护性

---

#### 2.2 数据分布技术

**1. 哈希散列的问题**

* 扩展性差，节点变化需大量数据迁移
* 解决方案：

  * 扩充哈希位数，改变哈希函数
  * **一致性哈希算法**

**2. 一致性哈希**

* 每个节点分配token，构成哈希圆环
* 数据存储在顺时针方向的第一个节点
* 添加/删除节点只影响相邻节点，产生少量数据迁移

**3. 负载均衡**

* 节点定时向主控节点发送心跳数据包
* 主控节点监控CPU、内存、磁盘、网络资源利用率及数据读写情况

---

#### 2.3 复制与一致性

**复制技术：**

* 将主副本数据复制到其他节点生成备用副本
* 通过操作日志回放实现主副本到备副本的增量复制
* 保证可用性、可靠性、安全性

**两种复制技术：**

* **强同步复制**：写操作同步到所有副本才返回成功
* **异步复制**：写操作先返回，后台异步同步

**容错机制 - 故障检测：**

* **心跳检测**：总控节点向工作节点发送心跳包
* **缺陷**：网络问题导致误判
* **解决方案 - 租约机制**：主控节点发放租约，过期则停止服务

---

#### 2.4 分布式键值系统 - Dynamo

**1. 数据分布**

* 使用一致性哈希算法将数据分布到多个存储节点
* **虚拟节点**：每个物理节点根据性能分配多个token，解决节点异构性

**2. 复制与一致性**

* 每个数据项复制到N个主机（N为配置参数）
* 协调器节点负责复制其范围内的数据项
* 提供**最终一致性**：允许更新异步传播到所有副本

**3. 向量钟（Vector Clock）**

* 捕捉同一对象不同版本之间的因果关系
* 结构：（节点，计数）的链表
* 计数器初始为0，节点每次更新操作加1

**向量钟示例：**

```
Sx写操作 → D1([Sx,1]) → D2([Sx,2])
              ↓
        Sy写 → D3([Sx,2],[Sy,1])
              ↓
        Sz写 → D4([Sx,2],[Sz,1])  ← 冲突！
              ↓
        调和 → D5([Sx,3],[Sy,1],[Sz,1])
```

**冲突解决方法：**

* 客户端逻辑解决（如购物车应用）
* "Last Write Wins"：选择时间戳最新的副本（依赖时钟同步）

---

#### 2.5 Merkle树

**定义：** 存储hash值的树，叶子是数据块的hash值，非叶节点是子节点串联字符串的hash

**作用：**

* 快速一致性验证（比较根hash）
* 快速定位不一致的数据块
* 只同步差异数据，减少网络传输

---

#### 2.6 新型存储器件驱动的内存系统

**内存计算模式：**

* 以大数据为中心，依托硬件发展和软件体系结构革新
* 数据初始阶段全部加载到内存，查询操作在内存中执行
* CPU直接从内存读取数据，避免I/O操作
* 减少磁盘访问，降低网络延迟和磁盘I/O影响

**DRAM内存计算面临的挑战：**

1. **易失性**：数据持久化依赖外存，I/O瓶颈无法完全消除
2. **刷新操作**：周期性刷新限制可扩展性
3. **存储密度低**：单芯片存储密度达上限
4. **能耗高**：内存功耗可达全系统的46%

**NVM（非易失性存储器）特性：**

* 非易失性（断电不丢失）
* 字节寻址
* 存储密度高
* 功耗低
* 但访问速度和使用寿命不如DRAM

**异构内存系统（DRAM+NVM）：**

|架构|结构|特点|
|-|-|-|
|**平行结构**|DRAM与NVM同时作为主存|热页在DRAM，冷页在NVM|
|**层次结构**|NVM作为主存，DRAM作为缓存|热页迁移到DRAM|

### 第三章 大数据管理

#### 3.1 大数据管理挑战

**数据类型：**

* **结构化数据**：数据间有很强的因果关系
* **半结构化数据**：数据间因果关系较弱
* **非结构化数据**：数据间无因果关系

**新需求：**

1. 支持高并发读写
2. 支持海量数据的高效率存储和访问
3. 高可扩展和高可用性（秒级恢复，7×24小时不间断）

---

#### 3.2 大数据的划分 - CAP理论

**CAP三要素：**

* **C（一致性）**：系统保持数据一致
* **A（可用性）**：系统处于可用状态
* **P（分区容忍性）**：存在多个数据分区时仍能满足一致性和可用性

**CAP定理：** 分布式系统不可能完全同时满足C、A、P三个要素，必须取舍

**工程实践：**

* 分区容错性（P）是必选项（网络不可靠）
* 在满足分区容错的前提下，没有算法能同时满足数据一致性和服务可用性
* 一致性有不同级别：强一致性、序列一致性、最终一致性

**一致性级别：**

* **强一致性**：多节点像单节点一样运作，操作具备原子性
* **序列一致性**：不要求时序一致，但操作顺序保持一致
* **最终一致性**：放宽时间要求，某个时间点后所有副本最终达成一致

### 第四章 大数据编程

#### 4.1 函数式编程

**高阶函数：**

* 函数可以作为参数传入另一个函数
* 函数可以作为返回值
* 操作其他函数的函数

**函数合成：**

* 将已有函数组合成新函数
* f(x)和g(x)合成为g·f(x) = g(f(x))

**函数柯里化：**

* 把接受多个参数的函数变成接受单一参数的函数
* 返回接受余下参数且返回结果的新函数
* 对高阶函数的降阶处理

**惰性求值（延迟计算）：**

* 调用函数时不立即计算所有实参
* 先进入函数体，需要时才计算实参值
* 目的：避免无用计算
* 支持并行（a和b的计算可延迟到需要a+b时才执行）

---

#### 4.2 MapReduce编程

**编程接口：**

```
map: <k1, v1> → list(<k2, v2>)
reduce: <k2, list(v2)> → list(<k3, v3>)
```

**体系结构：**

* **Client**：提交作业
* **JobTracker**：资源管理和任务调度
* **TaskTracker**：执行任务
* **Task**：Map Task / Reduce Task

**优点：**

* 编程容易，不需要掌握分布式并行编程细节
* "分而治之"策略，数据集切分成多个split并行处理

**缺点：**

* 表达能力有限
* 磁盘I/O开销大
* 延迟高
* 难以胜任复杂、多阶段的计算任务

---

#### 4.3 Spark

**与Hadoop对比优点：**

1. 计算模式不限于Map和Reduce，支持流处理、图等，编程模型更灵活
2. 内存计算，中间结果放内存，迭代运算效率更高
3. 基于DAG的任务调度优于批处理执行机制

**运行基本流程：**

1. Driver创建SparkContext，进行资源申请、任务分配和监控
2. 资源管理器为Executor分配资源，启动Executor进程
3. SparkContext根据RDD依赖关系构建DAG图，提交给DAG Scheduler解析成Stage，TaskSet提交给TaskScheduler
4. Executor申请Task，Task Scheduler发放Task并提供应用程序代码
5. Task在Executor上运行，结果反馈给TaskScheduler和DAG Scheduler，完成后写入数据并释放资源

**RDD（弹性分布式数据集）：**

* 只读、可分区的数据集合
* 典型执行过程：创建 → 转换(Transformation) → 动作(Action)
* **Lineage（血缘关系）**：DAG拓扑排序结果

**RDD优点：**

* 惰性调用、管道化、避免同步等待
* 不需要保存中间结果
* 高效的容错性（血缘关系、重新计算丢失分区）
* 中间结果持久化到内存
* 存放的数据可以是Java对象，避免序列化/反序列化

**RDD依赖关系：**

* **窄依赖**：父RDD一个分区对应子RDD一个分区（或多个父对应一个子）
* **宽依赖**：父RDD一个分区对应子RDD多个分区

**Stage划分：**

* 根据RDD分区的依赖关系划分Stage
* 窄依赖的操作可以流水线执行
* 宽依赖需要Shuffle，划分新的Stage

### 第五章 流处理

#### 5.1 流处理基础

**数据流：** 无序的数据序列，现实生活中无处不在

**流处理：** 以数据流为输入，通过计算机技术分析产生有用信息

**为什么需要流处理：**

* 实时处理每一个元素
* 省略存储到静态数据库的过程
* 数据产生的同时进行查询、处理、分析
* 应用处理延时大大降低

**流处理系统：** Apache Storm、Spark Streaming、Apache Flink

**分布式流计算重要步骤：**

1. 数据封装：将待处理数据封装为连续数据流模式
2. 建立应用拓扑：将应用逻辑转化为一组由起始、终止和中间操作组成的应用拓扑图
3. 指定操作并行度：为了充分利用分布式集群的高并行计算能力，每个操作在系统中可以由多个线程同时运行，提高吞吐率
4. 指定数据分组和传输方式：由于操作多实例化，需要进一步指定流数据的分组和传输方式，保证所有数据被正确完整处理

**Storm：WordCount应用编程示例：**

1. 实现生成数据的spout，封装数据：首先构建一个CreateSentenceSpout来进行数据流的生成
2. 实现对流数据进行操作处理的bolt：在WordCount应用中，对spout生成的句子，构建两个bolt来进行处理：一个SplitWordBolt来将句子划分为单词，一个CountBolt来对划分好的单词进行累计计数
3. 构建流应用Topology，并指明并行度和分组策略：实现了对应的spout和bolt功能之后，最后就是将其连接成一个完整的Topology

---

#### 5.2 开源系统及编程思想

**1. Apache Storm**

* **Spout**：数据源组件，封装数据
* **Bolt**：数据处理组件
* **Topology**：流应用拓扑，连接Spout和Bolt

**2. Spark Streaming**

* 将数据流划分为微批（Micro-batch）
* 用离散流（D-Stream）形式表示流计算
* 每批输入数据转化为RDD
* 沿用Spark Core的RDD transformation操作

**系统框架组件：**

* **Master**：流应用入口
* **Client**：将数据传入系统
* **Worker**：流数据入口，执行RDD转换

**3. Apache Flink**

* **JobClient**：独立的程序执行入口
* **JobManager**：对应一个Flink程序的master进程，负责job管理和资源协调
* **TaskManager和TaskSlot**：具体负责执行task的组件

#### 5.3 流处理一致性语义

|语义|定义|适用场景|
|-|-|-|
|**At Most Once（至多一次）**|元组要么被处理一次，要么被丢弃，不会重复处理|统计分析，对完整性要求不高|
|**At Least Once（至少一次）**|元组至少被处理一次，不丢失，但可能重复|安全监测，要求完整性和安全性|
|**Exactly Once（恰好一次）**|元组恰好被处理一次，不重复不丢弃|金融交易，对数据处理非常敏感|

**Exactly Once实现：**

* 对数据进行持久化存储
* 对数据处理过程中产生的所有状态信息进行持久化存储

### 第六章 图计算

#### 6.1 图计算背景

**图计算 vs 传统应用：**

|特性|传统应用|图计算应用|
|-|-|-|
|计算/访存比|计算密集|较低|
|访存模式|顺序访存|大量随机访存|
|数据依赖|数据并行性高|复杂数据依赖|
|数据分布|局部性好|非结构化分布|

**图计算难点：**

* 每个点计算量少，难以掩盖内存访问延迟
* 大量随机访存请求
* 探索并行性困难，存在大量数据冲突
* 点度数分布不均衡，负载均衡问题和通信开销严重

---

#### 6.2 存储结构

**1. 邻接矩阵**

* 实现：二维数组
* 优点：容易判定两点关系，容易求得顶点度数
* 缺点：占用空间大O(|V|²)，边数少时浪费严重

**2. 边表**

* 实现：数组
* 优点：相较邻接表局部性更好
* 缺点：不易得到顶点度数，不易判定两点关系
* 空间复杂度：O(2|E|)

**3. 邻接表**

* 实现：链表
* 优点：消除空边冗余存储，容易得到顶点出度
* 缺点：不易得到顶点入度，不易判定两点关系
* 空间复杂度：O(|V|+|E|)

**4. CSR（压缩稀疏行存储格式）**

* 实现：数组（行指针、列索引、边数据）
* 优点：相较边表消除冗余源点信息，边局部性好
* 空间复杂度：O(|V|+|E|)

---

#### 6.3 图计算并行编程模型

**主流编程模型：**

|模型|特点|
|-|-|
|**以点为中心**|细粒度并行，每个点收取、更新、分发信息|
|**以边为中心**|顺序访存，负载均衡，细粒度并行|
|**以路径为中心**|顺序访存，分散(scatter)和整合(gather)操作|
|**以子图为中心**|粗粒度，先划分子图，更新子图内所有点|

**以点为中心的模型：**

* 三个操作：收取信息、更新信息、分发信息
* 分为：一阶段、二阶段、三阶段编程模型
* 计算过程分割为多个超级步，超级步之间通过屏障保证信息同时传送和接收

**以边为中心的Scatter-Gather模型：**

* 函数输入是图中的边，遍历所有边
* 将源顶点的最新信息通过边传送出去
* 负载均衡、细粒度并行、顺序的边访问

**以点为中心 vs 以边为中心：**

|特性|以边为中心(EC)|以点为中心(VC)|
|-|-|-|
|算法表达|可以表示多种图算法|能够容易表示大多数图算法|
|边访问|顺序的|大量随机访存|
|点访问|大量随机访问|点处理并行性较高|
|计算|边的冗余计算|数据冲突频繁|

**以子图为中心的模型：**

* 粗粒度编程模型
* 先把图划分为不同子图
* 更新子图中所有点直到子图收敛
* 最后把子图更新状态传送到其他子图
* 典型系统：Blogel、Giraph++、GoFFish、BlockGRACE

---

#### 6.4 图划分和通信

**图划分目标：**

* 保证负载均衡
* 减少边跨越划分块的次数
* 最大化每个计算节点的计算效率

**图划分难点：**

* 图一般符合幂律分布，难以均匀分割
* 导致负载倾斜和数据局部性差
* 产生巨大通信开销

**图划分方法：**

**1. 以顶点为中心的划分（Pregel、GraphLab）**

* 把顶点均匀分布到每个计算节点
* 将同一个点的所有资源聚合在同一台机器
* **缺点**：负载不均衡（高度数节点）、难以划分、有限的并行性

**2. 以边为中心的划分**

* 把顶点作为处理对象，利用边传递信息
* **实现方法**：

  * 贪婪划分：如果边的点出现在某台机器上，优先向那台放置
  * 向数量少的机器放置

**3. 混合划分（Hybrid-Cut）**

* 出入度高的顶点采用切点法
* 出入度低的顶点采用切边法
* 性能提升1.24倍

**消息交互模式：**

|模式|特点|
|-|-|
|**Push**|以源顶点为中心，遍历源顶点，按出边广播消息给目标点，存在数据冲突|
|**Pull**|以目的顶点为中心，遍历目的顶点，根据入边请求消息数据，无数据冲突，但存在冗余计算|

**同步异步混合模式：**

* PowerSwitch利用在线采样与离线分析技术
* 动态预测两种模型的计算性能
* 建立代价收益模型，实现迭代过程中同步和异步计算的自动切换

#### 6.5 图算法案例

**广度优先搜索（BFS）：**

```
Procedure UPDATE(s,d): Parents[d]=s
Procedure COND(i): return(Parents[i] == -1)
Procedure EDGEPRO(G, U, F, C):
    Out = {}
    for v ∈ U do
        for ngh ∈ AdVertex(v) do
            if(C(ngh) == 1) then
                out = F(depth[]++, ngh)
    return Out
Procedure BFS(G, r):
    visited[r]=r
    Active = {r}
    while(SIZE(Active)≠ 0) do
        Active = EDGEPRO(G, Active, UPDATE, COND)
```

**单源最短路径（SSSP）：**

* Gather阶段：收集信息
* Update阶段：更新顶点状态
* Scatter阶段：分发信息

#### 6.6 Pregel图计算系统

**图划分：**

* 将图划分成许多partitions
* 每个partition包含一些顶点和以这些顶点为起点的边
* 默认partition函数：hash(ID) mod N

**计算模型：**

* 第0个超步，所有顶点处于active状态
* 只有active顶点参与对应超步中的计算
* 顶点通过设置status为"halt"进入inactive状态
* inactive顶点收到消息被唤醒进入active状态
* 计算在所有顶点都达到"inactive"且无消息传送时结束

**消息传递模型：**

* 纯消息传递模型，忽略远程数据读取和共享内存
* 原因1：消息传递模型足够表达所有图算法
* 原因2：性能考虑，远程读取延迟高，消息传递通过异步批量传输减少延迟

**Pregel vs MapReduce：**

* Pregel将PageRank处理对象看成连通图，MapReduce看成Key-Value对
* Pregel将计算细化到顶点，控制循环迭代次数；MapReduce批量化处理，按任务进行循环控制
* PageRank用MapReduce实现需要一系列调用，传递整个图状态，通信和序列化开销大
* Pregel使用超步简化了过程

---

#### 6.7 分布式图计算系统问题

**同步模型：**

* 需要栅栏（barrier）协调多个计算节点的计算进度
* 较快的节点会等待较慢的计算节点

**异步模型：**

* 存在潜在数据冲突
* 需要进行原子保护（atomic）操作

#### 6.8 单机图计算

**图计算系统分类：**

1. 多机内存图计算系统
2. 多机外存图计算系统
3. 单机内存图计算系统
4. 单机外存图计算系统

**基于CPU的单机内存：GraphMat**

* 编程模型与传统以点为中心的模型对应
* 单源最短路径实现：

  * **SEND_MESSAGE()**：每轮迭代生成稀疏向量记录激活点
  * **PROCESS_MESSAGE()**：将稀疏向量中的值与边距离相加
  * **Reduce()**：进行最小化比较操作
  * Process Message和Reduce共同组成**稀疏矩阵向量乘**操作

**图数据存储格式：**

* **DCSC（双重压缩稀疏列格式）**
* **CSR（压缩稀疏行存储格式）**
* 采用矩阵形式存储十分稀疏的图数据，浪费空间

**单机外存：**

* 以边为中心进行编程
* 存在大量冗余数据加载的问题

**单机异构：Scaph实例（基于"存储思维"的图计算系统）**

根据子图的使用价值，对子图数据类别进行细分：

|数据类别|含义|特征|
|-|-|-|
|**有用数据（UD）**|本轮迭代中一定会被使用|与活跃顶点相邻边集合|
|**潜在有用数据（PUD）**|后续迭代过程中会被使用|后续迭代UD数据之和|
|**无用数据（NUD）**|本轮及后续迭代都不会被使用|源顶点已经收敛|

**按价值传输策略：**

* **高价值子图**：整图传输（含有用数据和潜在有用数据含量高）
* **低价值子图**：精简后传输（无用数据含量较高）

### 第七章 大数据系统资源管理与协调技术

#### 7.1 统一资源管理

**面临的挑战：**

**挑战1：针对不同应用进行合理的资源分配、提高系统资源利用率**

* 每个框架有不同的编程、通信模型，任务间依赖关系和数据放置方法及资源需求粒度都不尽相同
* 2010年Facebook数据处理平台检测结果显示，Map任务对CPU资源需求较高，Reduce任务需要更多内存资源

**挑战2：为多种计算框架同时提供基础保障**

* 每种计算框架针对的应用特征不尽相同，偏好的调度策略也不一样
* MapReduce任务执行过程中任务大小分布存在长尾特征，小作业优先的调度策略容易造成大作业饿死
* I/O密集型和计算密集型等不同应用中，单纯按某一资源有限的调度策略会造成性能损失

**挑战3：统一资源管理系统可容错、高可用**

* 分布式系统中所有应用程序都依赖于统一资源管理系统
* 可通过配置ZooKeeper等协调系统在多个备份主控服务器中进行领导选举
* 当主控节点发生故障时，通过协调系统的选举机制选择新的主控节点

**基本架构：**

统一资源管理系统包含以下核心组件：

* **作业组织**：接收、组织和管理用户提交的各种作业（如Hadoop、Spark等）
* **资源调度**：接收资源状态信息并回收空闲资源，更新资源池信息
* **资源组织**：管理节点的资源，向资源调度组件汇报目前节点资源使用状况

**架构组成：**

* **资源管理器（Resource Manager, RM）**：包含主进程、若干副本进程相互备份，管理每个集群节点上运行的slave进程
* **节点管理器（Node Manager）**：运行在slave节点上，负责汇报节点状态、管理容器
* **应用控制器**：运行在容器中，执行具体任务
* **容错管理**：保证系统高可用

**工作流程：**

* 计算框架在slave节点上运行
* RM主进程使用RO（Resource Offers）实现计算框架的细粒度共享
* 计算框架包含两部分：

  1. 注册到RM主进程的调度器，提供资源
  2. 运行于slave节点上的执行进程，用于运行计算框架的任务

#### 7.2 大数据系统资源调度

**资源调度目的：**

* 提高资源利用率
* 避免任务的死锁、饿死、资源碎片化、过分配
* 减少任务响应时间

**资源调度系统架构：**

* 单级资源调度器
* 两级资源调度器
* 共享状态调度器

**典型调度算法：**

1. **FIFO调度算法**
2. **延迟调度算法（Delay Scheduling）**
3. **主资源公平调度算法（Dominant Resource Fairness, DRF）**
4. **多资源打包调度算法（Multi-Resource Packing）**
5. **无私的资源调度算法（Altruistic Scheduling）**

**主资源公平调度算法（DRF）：**

* **目标**：保证不同的用户和应用公平地获得系统资源
* **典型实现**：最大最小公平分配策略
* **核心思想**：最大化具有最少主资源需求的作业或用户的资源量

**DRF算法伪代码：**

```
输入：
  R = (r1, r2, ..., rm)        // 集群总资源量
  D = (d1, d2, ..., dn)        // 每一个用户单个任务资源量
  m：资源类数，n：用户总数

输出：
  ui = (ui,1, ui,2, ..., ui,m) (i=1,...,n)  // 用户已经分配的资源量

步骤：
  si = 0 (i=1,...,n)           // 用户i已经分配的主资源
  选择具有最低主资源分量Si的用户i
  得到用户i的下一个任务的资源需求Di
  if C + di < R then
      C ← (C + di)             // 更新消耗的资源量
      ui ← (ui + di)           // 更新用户i分配到的资源量
      si ← max_{j=1..m}(ui,j / rj)  // 更新用户i分配到的主资源分量
  else
      return
  end if
```

**多资源打包调度算法：**

* **目的**：提升各种资源的利用率
* **核心思想**：在作业调度过程中考虑不同作业之间的互补性，将具有互补性的作业尽量分配到同一节点
* **效果**：避免某一种资源成为瓶颈，而其他资源利用率低

**无私的资源调度算法（利他调度算法）：**

* **基本原理**：采取长远的公平策略，而不是瞬时的公平策略
* 作业可以在不影响自身完成时间的基础上贡献出一部分剩余资源给其他作业
* 利用剩余资源提升应用性能指标和集群资源利用率

---

#### 7.3 大数据系统的协调技术

**协调系统架构：**

* 通过提供中心化共享数据的读写来为多节点提供协调服务
* 由若干台服务器构成，每台服务器内存中维护**相同的数据集合**
* 通过选举机制选择一台为主控服务器（领导者），其他为从属服务器
* 客户端连接任一台服务器，向其提交对服务器共享数据的读写请求

**Paxos算法：**

基本Paxos算法可以让所有节点就单个变量值达成一致。

**核心角色：**

* **Client**：产生要同步的数据值v
* **Proposer（提议者）**：生成递增序列号n
* **Acceptor（接受者）**：与当前最大提议序列号比较，决定是否接受

**核心阶段：**

**第一阶段：准备阶段（Prepare Phase）**

* Proposer向Acceptor发送PrepareRequest（包含序列号n）
* Acceptor将n与当前最大提议序列号N1比较：

  * 如果 n > N1：更新N1 = n，响应"可接受提议"，携带最大已接受提议序列号N_max及提议值v2
  * 如果 n <= N1：拒绝提议

**Acceptor通过提案M的准备请求后的承诺：**

1. 不再通过编号小于等于M的提案的prepare请求
2. 不再通过编号小于M的提案的accept请求
3. 如果已通过某一提案，在prepare请求响应中返回已通过的最大编号提案内容；否则返回空值

**关键变量：**

* **minProposal**：当前Acceptor在prepare请求中通过的最大提案编号
* **acceptedProposal**：当前Acceptor在accept请求中通过的最大提案编号
* **acceptedValue**：当前Acceptor在accept请求中通过的最大提案编号的提案值

**第二阶段：接受阶段（Accept Phase）**

* Proposer在prepare阶段收到大多数响应后，向Acceptor发送AcceptRequest（包含seq和val）
* 如果Acceptor没有通过编号大于M的prepare请求，则批准提案(M, V)
* 如果Acceptor已经通过编号大于M的prepare请求，则拒绝提案(M, V)
* 当超过半数Acceptor响应接受后，数据达成一致

---

**Raft算法：**

**概述：**

* Raft从多副本状态机的角度提出，用于管理多副本状态机的日志复制
* 实现和Paxos相同的功能，将一致性分解为多个子问题：

  1. Leader选举
  2. 日志同步
  3. 安全性
  4. 日志压缩
  5. 成员变更

**角色划分：**

|角色|功能|
|-|-|
|**Leader（领导者）**|接受客户端请求，向Follower同步日志，日志同步到大多数节点后告诉Follower提交|
|**Follower（跟从者）**|接受并持久化Leader同步的日志，Leader告知可提交后提交日志|
|**Candidate（候选人）**|Leader选举过程中的临时角色|

* Raft要求系统在任意时刻最多只有一个Leader
* 正常工作期间只有Leader和Followers

**日志同步：**

* 日志由有序编号（log index）的日志条目组成
* 每个日志条目包含：任期号（term）+ 用于状态机执行的命令
* 如果一个日志条目被复制到大多数服务器上，就被认为可以提交（commit）

**Raft日志同步保证两点：**

1. 如果不同日志中的两个条目有着相同的索引和任期号，则它们所存储的命令是相同的
2. 如果不同日志中的两个条目有着相同的索引和任期号，则它们之前的所有条目都是完全一样的

**Leader崩溃与日志不一致处理：**

* Leader崩溃可能导致日志不一致（旧Leader可能没有完全复制完日志）
* **处理方式**：Leader通过强制Followers复制它的日志来处理不一致
* Leader从后往前试，每次AppendEntries失败后尝试前一个日志条目，直到找到一致位点，然后向后逐条覆盖

**安全性限制：**

**限制1：** 拥有最新的已提交的log entry的Follower才有资格成为Leader

**限制2：** Leader只能推进commit index来提交当前term的**已经复制到大多数服务器**上的日志，旧term日志的提交要等到提交当前term的日志来间接提交

**安全性问题示例：**

* 阶段a：term为2，S1是Leader，写入日志(2,2)，同步到S2
* 阶段b：S1离线，S5被选为Leader（term=3），写入日志(3,2)但未推送就离线
* 阶段c：S1重新上线被选为Leader（term=4），同步日志(2,2)到S3，此时已被多数节点确认
* 阶段d：S1又下线，S5可能被选为Leader（term=5），覆盖已提交的日志(2,2) —— **这就是已提交日志被覆盖的问题**

**增加限制后的效果：** 即使日志(2,2)已被大多数节点确认，但不能被提交（因为是旧term的日志）。直到S1在当前term(4)产生的日志(4,4)被大多数Followers确认，方可提交。此时S5不可能成为Leader（因为没有包含日志(4,4)）。

**日志压缩（Log Compaction）：**

* 不能让日志无限增长，否则系统重启需要很长时间回放
* Raft采用对整个系统进行**snapshot**来解决，snapshot之前的日志可以丢弃
* 每个副本独立地对自己的系统状态进行snapshot，只能对已提交的日志记录进行snapshot
* Snapshot包含：日志元数据（最后一条已提交log entry的log index和term）+ 系统当前状态
* 做snapshot推荐当日志达到某个固定大小时做一次
* 可通过**copy-on-write**技术避免snapshot过程影响正常日志同步

### 第八章 大数据系统优化

#### 8.1 存储优化-大数据处理分析应用执行具有I/O密集型特征

**多阶段作业缓存效果：**

* 两阶段MapReduce作业中，仅一个执行时间较长的map任务使得整个reduce阶段执行延后
* 最终导致作业执行时间延长

**全有/全无（all-or-nothing）缓存约束机制：**

* 需要缓存输入文件的所有数据分块，才能有效加速
* 主控节点需要全局协调，确保跨机器的不同分块统一缓存管理
* **机制设计目标：**

  * 支持数据块缓存的节点集合的查询
  * 跨机器全局协调缓存替换
* **算法思想：** 通过查找不完整缓存的文件，利用全局映射来实现

**PACMan系统：**

由一个中央协调器和位于集群存储节点的一组工作节点组成：

* **协调器**：全局协调对数据分块的缓存决策
* **工作节点**：访问内存数据块，以及缓存新的数据块

---

#### 8.2 调度优化-更好的任务执行计划,作业更快时间完成

**拖后腿问题（Straggler）：**

* **Straggler任务**：一个大的作业被切分为多个小任务并行执行，某些任务比同类型的其他任务执行慢很多
* 判断数据任务执行超时，将该数据从源头开始在拓扑中重新计算
* Spark的计算模型中，一个阶段必须等到所有节点该阶段的所有任务完成，才能进入下一阶段

**推测性调度执行机制（Speculative Execution）：**

* 通过利用更多的资源来换取时间的一种策略
* 大数据框架**为短板任务启动推测任务**，分发到**其他节点**上
* 备份任务与原始任务同时处理一份数据，先运行完的结果作为最终结果
* 运行完成后杀死另一个任务

**三种优化推测执行方法：**

|方法|特点|
|-|-|
|**LATE**|更新straggler的判断方法，优化执行决策|
|**Mantri**|偏向于对系统中的异常任务进行检测，实时检测及时采取决策|
|**Coworker**|采用协助的方法去加速straggler完成任务|

**Coworker vs Straggler：**

* Coworker与Straggler是**互补关系**
* Straggler处理一部分数据，Coworker在另一个节点上处理剩余数据
* Coworker在不浪费计算资源的情况下，同样能加快straggler的执行

---

#### 8.3 运行时优化-计算任务在节点运行优化来提升性能

**Shuffle阶段缓存：**

* 将map与reduce之间产生的磁盘文件缓存到内存中间数据
* 将shuffle产生的文件数据缓存到内存空间中，而不是直接写入磁盘

**迭代性应用缓存：**

* 将多次使用的关键性数据缓存到内存中，多见于迭代性应用
* Spark通过调用RDD的 **persist()** 方法来标记需要缓存的数据
* 通过调用 **unpersist()** 来移除缓存的数据
* 当持久化一个RDD，每个节点将计算的分片结果保存在内存中
* 后续操作加速约**10倍**

### 题目1：分析大数据5V特征的挑战与措施

**解答：**

**1. Volume（大容量）**

* **挑战：**

  * 存储成本高，传统存储设备容量有限
  * 数据处理速度慢，单机处理能力不足
  * 数据传输和备份困难
* **措施：**

  * 采用分布式存储系统（HDFS、Ceph）
  * 使用数据压缩和去重技术
  * 水平扩展，增加存储节点

**2. Velocity（快速性）**

* **挑战：**

  * 数据产生速度快，需要实时处理
  * 传统批处理无法满足时效性要求
  * 系统响应延迟要求高
* **措施：**

  * 采用流处理技术（Storm、Spark Streaming、Flink）
  * 内存计算减少磁盘I/O
  * 预处理和缓存热点数据

**3. Variety（多样性）**

* **挑战：**

  * 结构化、半结构化、非结构化数据混合
  * 数据格式不统一，难以整合
  * 多源异构数据融合困难
* **措施：**

  * 采用多模态数据融合技术
  * 使用NoSQL数据库（文档型、键值型、图数据库）
  * 数据标准化和ETL处理

**4. Value（价值低）**

* **挑战：**

  * 海量数据中只有少量有价值信息
  * 数据挖掘难度大，"大海捞针"
  * 需要复杂的分析算法提取价值
* **措施：**

  * 使用数据挖掘和机器学习算法
  * 建立数据仓库和数据湖
  * 采用智能分析平台（如Spark MLlib）
  * 结合领域专家知识进行分析

**5. Veracity（准确性）**

* **挑战：**

  * 数据来源多样，质量参差不齐
  * 存在噪声、错误、缺失值
  * 数据可信度难以保证
* **措施：**

  * 建立数据质量管理体系
  * 数据清洗（去噪、填充、去重）
  * 数据溯源和血缘追踪
  * 数据验证和审计机制

### 题目2：复制技术为什么带来一致性问题？如何保证多副本一致性？

**解答：**

**为什么带来一致性问题：**

1. **网络延迟**：副本间同步需要通过网络，存在延迟
2. **节点故障**：部分节点宕机导致副本不一致
3. **并发写入**：多个客户端同时修改同一数据
4. **分区容错**：网络分区时，不同分区内的副本无法同步

**保证一致性的方法：**

**1. 强同步复制**

* 写操作必须同步到所有副本才返回成功
* 优点：强一致性
* 缺点：延迟高、可用性降低

**2. 异步复制**

* 写操作先返回成功，后台异步同步副本
* 优点：延迟低、可用性高
* 缺点：可能读取到旧数据

**3. 租约机制（Lease）**

* 主副本持有租约才能处理写请求
* 租约过期后需要续租，保证主副本唯一性

**4. 向量钟（Vector Clock）**

* 记录事件的因果关系
* 检测并发冲突，支持冲突解决

**5. Quorum机制（NWR模型）**

* N：副本总数
* W：写入成功所需副本数
* R：读取所需副本数
* 当W + R > N时，保证读取到最新数据

**6. Merkle树**

* 快速定位不一致的数据块
* 只同步差异数据，减少网络开销

### 题目3：副本放置原则与集群环境下的多副本放置策略

**解答：**

**副本放置原则：**

**1. 可靠性原则**

* 副本分布在不同故障域（机架、机房、地域）
* 避免单点故障导致所有副本丢失

**2. 可用性原则**

* 副本分布在不同节点，保证读写可用
* 考虑网络拓扑，减少跨机架流量

**3. 负载均衡原则**

* 均匀分布副本，避免热点
* 考虑节点容量和性能差异

**4. 性能原则**

* 就近访问，减少网络延迟
* 考虑数据本地性

**HDFS副本放置策略（详细）：**

**副本距离计算公式：**

* Distance(Rack1/D1, Rack1/D1) = 0（同一台服务器）
* Distance(Rack1/D1, Rack1/D3) = 2（同一机架不同服务器）
* Distance(Rack1/D1, Rack2/D1) = 4（不同机架）

**放置规则：**

1. 第一个副本：在本节点（如果写请求方是DataNode）或随机选择
2. 第二个副本：在远端机架的节点
3. 第三个副本：如果前两个在同一机架，则选其他机架；否则选第一个副本同机架的不同节点
4. 第四个及以上：随机选择

### 题目4：简述分布式环境下CAP原理的内涵

**解答：**

**CAP原理：** 分布式系统不可能同时满足一致性（Consistency）、可用性（Availability）、分区容错性（Partition Tolerance）三个特性，最多只能同时满足其中两个。

**三要素内涵：**

**1. C - 一致性（Consistency）**

* 所有节点在同一时间看到的数据是一致的
* 写操作完成后，任何读操作都能读到最新值

**2. A - 可用性（Availability）**

* 每个请求都能在有限时间内获得响应
* 系统始终处于可用状态，不返回错误

**3. P - 分区容错性（Partition Tolerance）**

* 系统在遇到网络分区（节点间通信中断）时仍能继续运行
* 分布式系统中网络分区不可避免，因此P通常是必选项

**CAP权衡组合：**

|组合|特点|代表系统|
|-|-|-|
|**CP**|保证一致性和分区容错，牺牲可用性|HBase、MongoDB（配置为CP）|
|**AP**|保证可用性和分区容错，牺牲强一致性|Cassandra、DynamoDB|
|**CA**|保证一致性和可用性，无法容忍分区|传统单机数据库|

**工程实践中的折中：**

* 一致性有不同级别：强一致性、序列一致性、最终一致性
* 弱化一致性换取更好的可用性和性能

### 题目5：向量钟和Merkle树分别是什么？简述他们的作用

**解答：**

**向量钟（Vector Clock）：**

**定义：** 捕捉同一对象不同版本之间因果关系的机制，是一个（节点，计数）的链表。计数器初始为0，节点每次更新操作加1。

**工作原理：**

```
Sx写操作 → D1([Sx,1]) → D2([Sx,2])
              ↓
        Sy写 → D3([Sx,2],[Sy,1])
              ↓
        Sz写 → D4([Sx,2],[Sz,1])  ← 冲突！
              ↓
        调和 → D5([Sx,3],[Sy,1],[Sz,1])
```

**作用：**

* 检测同一对象不同版本之间的因果关系
* 识别并发冲突
* 支持冲突解决

**冲突解决方法：**

* 客户端逻辑解决（如购物车应用）
* "Last Write Wins"：选择时间戳最新的副本

---

**Merkle树（Hash Tree）：**

**定义：** 存储hash值的树，叶子是数据块的hash值，非叶节点是子节点串联字符串的hash。

**作用：**

* 快速一致性验证（比较根hash）
* 快速定位不一致的数据块
* 只同步差异数据，减少网络传输

---

### 题目6：NVM有什么特性？为什么要用DRAM和NVM一起构成异构内存系统？

**解答：**

**NVM（非易失性存储器）特性：**

* 非易失性（断电不丢失数据）
* 字节寻址（像内存一样访问）
* 存储密度高
* 功耗低
* 但访问速度和使用寿命不如DRAM

**DRAM面临的挑战：**

* 易失性：数据持久化依赖外存，I/O瓶颈无法消除
* 刷新操作：周期性刷新限制可扩展性
* 存储密度低：单芯片存储密度达上限
* 能耗高：内存功耗可达全系统的46%

**异构内存系统（DRAM+NVM）：**

|架构|结构|特点|
|-|-|-|
|**平行结构**|DRAM与NVM同时作为主存|热页在DRAM，冷页在NVM|
|**层次结构**|NVM作为主存，DRAM作为缓存|热页迁移到DRAM|

**为什么使用异构内存：**

* 弥补各自缺点：DRAM速度快但易失、能耗高；NVM非易失但速度慢
* 性能：热数据在DRAM中快速访问
* 持久性：数据可持久化到NVM
* 成本：相比纯DRAM方案成本更低
* 容量：NVM提供更大存储容量
* 功耗：整体功耗低于纯DRAM系统

### 题目7：内存计算模式是什么？为什么内存系统对大数据处理很重要？

**解答：**

**内存计算模式：**

* 以大数据为中心，依托硬件发展和软件体系结构革新
* 数据初始阶段全部加载到内存，查询操作在内存中执行
* CPU直接从内存读取数据，避免I/O操作
* 不同于传统内存缓存，主要区别在内存中存储和访问方式

**为什么内存系统对大数据处理很重要：**

**1. 性能提升**

* 减少磁盘数据访问
* 降低网络延迟和磁盘I/O影响
* 大幅提升数据吞吐量与数据处理速度

**2. 适合迭代计算**

* 机器学习、图计算需要多次迭代
* 中间结果保存在内存，避免重复读写磁盘
* Spark相比Hadoop MapReduce快10-100倍

**3. 实时处理需求**

* 流处理、实时分析需要低延迟
* 内存计算满足毫秒级响应要求

**4. 挑战：**

* 随着内存容量增加，器件成本、功耗、散热问题突出
* 总成本增速达到内存容量增速的10倍以上
* 解决方案：使用NVM异构内存

### 题目8：Dynamo如何对数据进行分区？

**解答：**

**Dynamo分区机制：**

**1. 一致性哈希分区**

* 使用一致性哈希算法将数据分布到多个存储节点
* 每个物理节点根据其性能差异分配多个token（虚拟节点）
* 每个虚拟节点的处理能力基本相当，随机分布在哈希空间中
* 数据按照哈希值落到某个虚拟节点负责的区域，存储在该虚拟节点对应的物理节点中

**2. 虚拟节点优势**

* 解决节点异构性问题
* 使数据均匀分布
* 负载均衡

**3. 复制机制**

* 每个数据项复制到N个主机（N为配置参数）
* 每个键值K分配给协调器节点
* 协调器复制其范围内的数据项到N-1个其他节点

### 题目9：什么是函数式编程？它有哪些特点？

**解答：**

**函数式编程：**

* 函数可以不依赖任何其他对象而独立存在
* 函数可以作为参数传入另一个函数
* 函数可以作为返回值返回给调用者

**核心特点：**

**1. 高阶函数**

* 操作其他函数的函数
* 函数是一等公民

**2. 函数合成**

* 将已有函数灵活组合成新函数
* 在更高层次上对问题抽象
* x通过f变换成y，y通过g变换成z，x和z关系就是g·f

**3. 函数柯里化**

* 把接受多个参数的函数变成接受单一参数的函数
* 返回接受余下参数且返回结果的新函数
* 对高阶函数的降阶处理

**4. 惰性求值（延迟计算）**

* 调用函数时不立即计算所有实参
* 先进入函数体，需要时才计算实参值
* 目的：避免无用计算

### 题目10：简述引用透明性、高阶函数、函数柯里化、惰性求值的内涵

**解答：**

**1. 引用透明性**

* 相同输入总是产生相同输出
* 无副作用，不依赖外部状态
* 纯函数天然具有引用透明性

**2. 高阶函数**

* 函数可以作为参数传递给其他函数
* 函数可以作为返回值
* 操作其他函数的函数

**3. 函数柯里化**

* 把接受多个参数的函数转换为接受单一参数的函数
* 返回接受余下参数的新函数
* 示例：`add(x,y,z)` → `curriedAdd(x)(y)(z)`

**4. 惰性求值**

* 延迟计算，只在需要时才求值
* 调用函数时不立即计算参数
* 进入函数体后，需要时才计算实参值
* 目的：避免无用计算，支持并行

### 题目11：简述Google MapReduce和Hadoop的异同点

**解答：**

**相同点：**

* 都基于MapReduce编程模型
* 都采用"分而治之"策略
* 都适用于大规模数据集的批处理

**不同点：**

|特性|Google MapReduce|Hadoop MapReduce|
|-|-|-|
|**性质**|内部系统，不开源|开源实现（Apache）|
|**文件系统**|GFS|HDFS|
|**生态系统**|内部工具链|丰富的开源生态|
|**可定制性**|受限|高度可定制|

**Pregel vs MapReduce：**

* Pregel将PageRank处理对象看成连通图，MapReduce看成Key-Value对
* Pregel将计算细化到顶点，控制循环迭代次数
* MapReduce批量化处理，按任务进行循环控制
* PageRank用MapReduce需要一系列调用，传递整个图状态，开销大
* Pregel使用超步简化了过程

### 题目12：MapReduce方案 - 抽取前100个最大数

class TopKMapper:
    def __init__(self, k=100):

    def map(self, key, value):

class TopKReducer:

### 题目13：简述at most once、at least once和exactly once三种语义保障

**解答：**

|语义|定义|适用场景|
|-|-|-|
|**At Most Once（至多一次）**|元组要么被处理一次，要么被丢弃，不会重复处理|统计分析，对完整性要求不高|
|**At Least Once（至少一次）**|元组至少被处理一次，不丢失，但可能重复|安全监测，要求完整性和安全性|
|**Exactly Once（恰好一次）**|元组恰好被处理一次，不重复不丢弃|金融交易，对数据处理非常敏感|

**Exactly Once实现：**

* 对数据进行持久化存储
* 对数据处理过程中产生的所有状态信息进行持久化存储

### 题目15：简述几种主要的图计算编程模型，并分析它们的优点和缺点

**解答：**

**1. 以点为中心的编程模型**

* 三个操作：收取信息、更新信息、分发信息
* 优点：能够容易表示大多数图算法，点处理并行性较高
* 缺点：存在对边的大量随机访存，数据冲突频繁

**2. 以边为中心的编程模型（Scatter-Gather）**

* 函数输入是图中的边，遍历所有边
* 优点：可以表示多种图算法，对边的访问是顺序的
* 缺点：存在对点的大量随机访问，边的冗余计算

**3. 以路径为中心的编程模型**

* 包含scatter和gather操作
* 优点：顺序访存

**4. 以子图为中心的编程模型**

* 粗粒度，先划分子图
* 优点：大大减少超级步，降低计算时间
* 典型系统：Blogel、Giraph++、GoFFish、BlockGRACE

### 题目16：采用Scatter-Gather编程模型，写出单源点最短路径算法SSSP的伪代码

**解答：**

```python
# 顶点数据结构
class Vertex:
    def __init__(self, id):
        self.id = id
        self.distance = float('inf')
        self.active = False

class SSSP:
    def __init__(self, graph, source):
        self.graph = graph
        self.source = source
        self.vertices = graph.get_vertices()
        self.vertices[source].distance = 0
        self.vertices[source].active = True
    
    def run(self):
        while self.has_active_vertices():
            # ========== Scatter阶段 ==========
            messages = []
            for vertex in self.vertices:
                if vertex.active:
                    for edge in self.graph.get_edges(vertex.id):
                        neighbor_id = edge.target
                        new_distance = vertex.distance + edge.weight
                        messages.append((neighbor_id, new_distance))
                    vertex.active = False
            
            # ========== Gather阶段 ==========
            for target_id, new_distance in messages:
                target_vertex = self.vertices[target_id]
                if new_distance < target_vertex.distance:
                    target_vertex.distance = new_distance
                    target_vertex.active = True
        
        return {v.id: v.distance for v in self.vertices}
```

### 题目17：幂律图高维度节点处理方式的缺陷

**解答：**

**幂律图特征：** 少数顶点具有大量边，大多数顶点只有少量边

**处理方式及缺陷：**

**1. 顺序处理**

* 缺陷：延迟极高，成为瓶颈，负载不均

**2. 发送消息接触大部分图**

* 缺陷：网络开销大，消息风暴，内存压力

**3. 共享状态异步执行**

* 缺陷：一致性问题，需要锁机制，死锁风险

**4. 共享状态同步执行**

* 缺陷：同步开销大，锁竞争，扩展性差

**解决方案：**

* 混合划分（Hybrid-Cut）：高度数顶点采用切点法，低度数采用切边法
* 性能提升1.24倍

### 题目18：观察多层划分算法的伪代码，理解Coarsening和Uncoarsening的意义

**解答：**

**Coarsening（粗化）：**

* 将原图逐步合并顶点，生成一系列规模更小的近似图
* 目的：降低问题复杂度，在最粗图上划分计算量小
* 保留图结构特征，避免局部最优

**Uncoarsening（细化/解粗化）：**

* 从最粗图的划分开始，逐步映射回原图
* 在每一层进行局部优化（Kernighan-Lin算法）
* 改善划分质量，减少边切割，平衡负载

**多层划分优势：**

* 全局+局部：粗化阶段全局视野，细化阶段局部优化
* 效率高：主要计算在最粗图，细化只需局部调整
* 质量好：边切割少，负载均衡
